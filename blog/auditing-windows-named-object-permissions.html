Auditing Windows Named Object Permissions: The Kernel ACLs Attackers Exploit

Windows mutexes, events, shared memory, and named pipes can expose cross-process privilege paths when their ACLs are weak. Learn how to audit named objects and prioritize real risk.

Windows securable objects are not limited to files, registry keys, and services. The Object Manager also assigns security descriptors to mutexes, events, semaphores, shared-memory sections, symbolic links, and other named kernel objects. Services use them for synchronization and inter-process communication. If a privileged process creates one with an overbroad discretionary access control list (DACL), a low-privilege user may be able to alter state, spoof data, cause denial of service, or influence code running as SYSTEM.

This is an uncomfortable audit surface because the objects are temporary, application-specific, and scattered across namespaces. It is also exactly why insecure defaults survive for years: conventional file and registry scanners never see them.

How weak object ACLs become attack paths

Named objects live under namespaces such as \BaseNamedObjects, per-session directories, and Global\. The creator supplies a security descriptor; if it does not, Windows derives one from the process token. Problems appear when developers grant broad rights to Everyone, Authenticated Users, or ordinary local users so processes in different sessions can communicate.

  • Mutexes and events: An attacker can open, signal, reset, or delete synchronization objects, changing a privileged application's execution order or availability.
  • File-mapping sections: Writable shared memory can let an untrusted process modify commands, configuration, or serialized data consumed by a service.
  • Symbolic links and object directories: Creation or write rights can support namespace squatting and redirection attacks.
  • Named pipes: Weak pipe ACLs can expose privileged RPC-like interfaces; impersonation behavior and server validation add separate risks.
A permissive ACL is not automatically exploitable. Risk comes from the combination of a privileged owner, dangerous granted rights, attacker-controlled data, and a consumer that trusts the object.

Build an audit that survives real environments

Start by enumerating named objects while the target workload is active. A boot-time snapshot misses objects created only during updates, logon, backup jobs, or application transactions. Capture the object type, full namespace path, owner, integrity context, creator process when available, and the complete DACL. Repeat under representative workflows and compare snapshots.

Next, resolve every access control entry to a SID and effective principal. Flag low-privilege groups with modification-class rights rather than treating every readable object as critical. The important permissions vary by object type: SECTION_MAP_WRITE on a shared section, EVENT_MODIFY_STATE on an event, or broad generic access on an object directory deserves more attention than query-only access.

Prioritize with context, not ACL text alone

A useful triage model asks four questions:

  1. Is the creator or consumer running elevated, as a service account, or as SYSTEM?
  2. Can a standard user modify state, write shared data, create children, or replace the object?
  3. Does the privileged process trust object contents or make security decisions from them?
  4. Is the name predictable enough for pre-creation or squatting before the legitimate process starts?

Correlate suspicious objects with service configuration, executable signatures, process ancestry, and session boundaries. Preserve a baseline so newly introduced objects or ACL changes stand out after software upgrades. For ephemeral findings, retain timestamps and process identifiers; an object that vanishes before review is otherwise impossible to reproduce.

Fix the producer, then prove the boundary

The durable fix belongs in the process that creates the object. Define an explicit security descriptor granting only the identities and object-specific rights required. Prefer service SIDs or tightly scoped application groups over broad built-in groups. Use unpredictable names only as defense in depth; secrecy is not authorization. For shared memory and pipes, validate message lengths, state transitions, caller identity, and protocol semantics even after the ACL is corrected.

Test remediation from both sides: confirm the intended client still works, then verify a standard-user process cannot obtain the dangerous access mask. Monitor after deployment because vendor updates can recreate objects with default permissions.
