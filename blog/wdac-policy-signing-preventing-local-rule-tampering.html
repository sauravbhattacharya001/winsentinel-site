Windows Defender Application Control Policy Signing: Preventing Local Rule Tampering

Learn how signed WDAC policies protect Windows application-control rules from local administrator tampering, and how to deploy them safely across a fleet.

Windows Defender Application Control (WDAC) is strongest when it defines which code may execute, not merely which files an antivirus engine currently distrusts. But an unsigned WDAC policy has an uncomfortable boundary: a sufficiently privileged local actor may be able to replace or weaken the policy. Signing changes that boundary by making policy authenticity part of enforcement.

What policy signing actually protects

A signed WDAC policy carries a digital signature from a certificate your deployment process controls. Windows validates that signature before accepting policy updates. This helps prevent a local administrator, compromised management script, or attacker with SYSTEM-level access from swapping in a permissive policy through the normal update path.

Signing does not make an endpoint invulnerable. Firmware compromise, vulnerable kernel drivers, stolen signing keys, and an unsafe recovery process remain serious risks. The practical goal is narrower and valuable: policy changes must come from your trusted release pipeline rather than any process that can write a file locally.

The operational trade-off

Unsigned policies are easier to recover from during early testing. Signed policies deliberately remove some convenient escape hatches. A malformed rule set, expired signing certificate, or lost private key can turn a security control into an outage. Treat signing as the final stage of application-control maturity, after inventory and audit-mode evidence are stable.

Do not sign your first WDAC policy. Sign the policy whose audit telemetry, rollback path, and update process you have already exercised.

A safe deployment sequence

  1. Build from observed software inventory. Include Windows components, approved applications, deployment tools, drivers, scripts, and the software-updater paths that will maintain them.
  2. Run in audit mode. Review Code Integrity events across representative hardware and user personas. Resolve unexplained denials instead of broadly allowing writable directories.
  3. Enforce unsigned first. Prove that applications, servicing, feature updates, boot, and emergency administration continue to work.
  4. Create a dedicated signing identity. Use a code-signing certificate whose private key is non-exportable where possible. Separate policy authoring from signing approval and keep the key off ordinary admin workstations.
  5. Sign and canary. Deploy to a small ring with physical or out-of-band recovery access. Validate normal policy updates and an intentional rollback before expanding.
  6. Promote in waves. Track enforcement events, help-desk impact, update success, and policy version on every ring.

Design the signing pipeline like production code

The XML source, compiled policy, signature, certificate chain, and deployment manifest should be reproducible artifacts. Require peer review for rule changes, record hashes, and publish monotonically increasing versions. The signer should accept only reviewed artifacts from the build process—not arbitrary files from an operator's desktop.

Protect the private key with hardware-backed storage or a tightly controlled signing service. Limit who can request signatures, alert on unusual signing volume, and preserve logs long enough to support incident response. Rotate certificates before expiry while the old signing path still works; testing key rollover during a crisis is an avoidable gamble.

Recovery must be designed before enforcement

Document how responders recover a machine that cannot accept a new policy. Depending on platform and policy options, that may require Windows Recovery Environment, offline servicing, firmware access, or reimaging. Protect recovery credentials, test the procedure on each hardware class, and distinguish a supported rollback from an attacker-friendly bypass.

  • Keep a known-good signed policy and its exact deployment instructions.
  • Verify BitLocker recovery material is escrowed and accessible to authorized responders.
  • Test feature updates, driver changes, and management-agent upgrades in the canary ring.
  • Monitor for policy file changes, signature failures, and endpoints reporting stale versions.

From one endpoint to fleet assurance

That distinction matters for signed WDAC. The cryptography protects policy authenticity; fleet operations prove that the intended version reached every endpoint and stayed there. Alert when a canary stops reporting, a node falls behind, or adjacent controls such as Secure Boot and vulnerable-driver protections regress. Signing establishes trust in the policy. Continuous verification establishes trust in the deployment.
