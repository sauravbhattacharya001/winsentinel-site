Windows Defender Credential Theft Protection: Auditing Remote Credential Guard at Scale

Learn how Remote Credential Guard keeps reusable credentials off RDP targets, how to audit its prerequisites and policy, and how to detect fleet-wide drift.

Remote Desktop is indispensable for Windows administration, but a normal RDP sign-in can place reusable credentials on the destination host. If that server is already compromised, an attacker may steal the administrator's ticket material or derived secrets and turn one maintenance session into lateral movement. Windows Defender Remote Credential Guard changes that trust boundary: authentication requests are redirected back to the source device, so reusable credentials are not sent to the remote host.

What Remote Credential Guard actually protects

Remote Credential Guard uses Kerberos single sign-on while keeping the user's credentials on the client. The RDP server receives access to the resources the user is authorized to use, but it does not receive a reusable credential that can be harvested from LSASS. This is especially valuable for privileged administrators who must connect from a hardened access workstation to servers of varying trust.

It is not a universal shield. Both endpoints must be domain joined, Kerberos must work, the client must support the feature, and the destination must permit delegation. It also does not make a malicious destination safe: the server can still capture what the administrator types, alter displayed data, or abuse actions performed during the session. Treat it as credential isolation, not destination attestation.

Audit the policy, not just the checkbox

On clients, the decisive policy is Restrict delegation of credentials to remote servers. Its registry representation is:

reg query "HKLM\SOFTWARE\Policies\Microsoft\Windows\CredentialsDelegation" /v RestrictedRemoteAdministration

A value of 1 requires Restricted Admin mode; 2 prefers Remote Credential Guard. For most domain environments, 2 is the stronger operational choice because it preserves Kerberos-backed single sign-on without exposing reusable credentials to the target. Administrators can also test explicitly with:

mstsc.exe /remoteGuard

Do not stop at that value. Validate the prerequisites that determine whether protection really works:

  • The source and destination are joined to the same Active Directory domain or trusted domains.
  • DNS and time synchronization allow Kerberos to succeed; IP-address connections commonly fall back or fail.
  • The destination has Remote Desktop enabled and Network Level Authentication required.
  • Credential Guard is enabled on privileged workstations where hardware and application compatibility permit it.
  • Administrators do not bypass the control with saved .rdp files or alternate clients that omit Remote Credential Guard.

Verify behavior instead of trusting policy deployment

A GPO report only proves intent. Test from a representative privileged workstation using the server's DNS name, then inspect the resulting logon. Security event 4624 should show a remote interactive logon, while Kerberos events and ticket activity should be consistent with domain authentication. Investigate NTLM fallback, connections by IP address, and repeated Kerberos errors; each can indicate that the protected path is not operating as designed.

Remote Credential Guard should be the default administrative path, not an optional command-line trick remembered only during an incident.

Turn one setting into a fleet control

At fleet scale, the risk is drift. A newly imaged admin laptop misses the GPO, a troubleshooting exception becomes permanent, or a server team disables NLA. Build a control that evaluates source policy, domain membership, NLA, Kerberos prerequisites, and exceptions together. Prioritize machines used by highly privileged groups, because one unprotected RDP session from those devices has disproportionate blast radius.

A defensible rollout sequence

  1. Inventory privileged RDP source devices and target servers.
  2. Fix DNS, time, SPN, and trust issues before enforcing the policy.
  3. Pilot RestrictedRemoteAdministration=2 with a small administrator group.
  4. Monitor Kerberos failures and NTLM fallback during the pilot.
  5. Expand enforcement, continuously alert on policy and NLA drift, and document approved exceptions with owners and expiry dates.

The goal is not merely to enable a Windows feature. It is to ensure that privileged RDP never turns a compromised server into a credential collection point—and to detect quickly when any endpoint stops honoring that rule.
