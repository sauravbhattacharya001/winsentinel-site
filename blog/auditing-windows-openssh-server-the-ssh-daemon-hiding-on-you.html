Auditing Windows OpenSSH Server: The SSH Daemon Hiding on Your Windows Fleet

Windows OpenSSH Server is easy to enable and easy to forget. Audit sshd_config, keys, forwarding, firewall scope, and logging before port 22 becomes your blind spot.

Windows ships with an OpenSSH server you can enable in two clicks, and that convenience is exactly why it deserves an audit. Since Windows 10 1809, Microsoft has bundled OpenSSH as an optional feature, and on Windows 11 and Server 2022 it is one Settings toggle or one DISM command away from listening on port 22. For administrators who manage Linux and Windows side by side, that is genuinely useful. For attackers, it is a second remote access door on a machine that already has RDP, WinRM, and SMB — one that many Windows hardening baselines simply forget to mention.

The risk is not that SSH is insecure. The risk is that it arrives with defaults designed for getting started, not for staying safe, and that it tends to be enabled informally — by a developer who wanted to scp a file, by a vendor installer, or by an admin following a blog post — and then never revisited. If you have not deliberately decided your SSH posture, you do not have one. You have whatever the installer left behind.

What an attacker gets from a neglected sshd

An exposed Windows SSH server gives an attacker three things at once. First, a password-guessing surface that sits outside the usual Windows logon protections. Account lockout policies still apply to local accounts, but SSH attempts do not generate the same noisy trail of Event 4625 logon failures that defenders watch for RDP — they land in the OpenSSH operational log, which most SIEM onboarding never collects. Second, a shell. A successful SSH logon drops the attacker into PowerShell or cmd with the full rights of the account, and from there every living-off-the-land binary on the box is available. Third, a tunneling platform. SSH port forwarding turns a compromised workstation into a pivot into whatever else that workstation can reach, without the attacker ever touching RDP.

None of this requires a zero-day. It requires port 22 reachable, password authentication left on, and a credential that is weak, reused, or phished. That combination is common enough that internet-wide scans routinely find Windows SSH servers accepting password logons for administrator accounts.

The five checks that matter most

Start with the simplest question: should this machine run an SSH server at all? On a standard user workstation, the answer is almost always no. The feature should be absent, not merely stopped. A stopped service can be started by anyone who gains local admin; an uninstalled feature cannot. Check with Get-WindowsCapability -Online | Where-Object Name -like 'OpenSSH.Server*' and remove it where it is not needed.

Where SSH is genuinely required — jump hosts, build machines, cross-platform admin boxes — work through these settings in C:\ProgramData\ssh\sshd_config:

  • Disable password authentication. Set PasswordAuthentication no and ChallengeResponseAuthentication no, and require public-key authentication. Keys live in %USERPROFILE%\.ssh\authorized_keys for standard users and in C:\ProgramData\ssh\administrators_authorized_keys for administrators — that second file is the one auditors miss, and a stale key in it is standing admin access.
  • Restrict who can log on. Use AllowGroups or AllowUsers to limit SSH to a named admin group. By default, any local account can authenticate over SSH, including accounts that were never meant to have remote access.
  • Turn off forwarding unless you need it. AllowTcpForwarding no, AllowAgentForwarding no, and X11Forwarding no close the pivot paths. If a workflow needs forwarding, scope it to specific users with a Match block rather than enabling it globally.
  • Constrain the shell and session. Set MaxAuthTries 3, a short LoginGraceTime, and ClientAliveInterval so idle sessions do not linger. Consider ForceCommand or a restricted default shell for service accounts that only need file transfer — SFTP-only access is a common requirement that does not need a full shell.
  • Fix the firewall rule. The installer creates an inbound rule for port 22 scoped to any profile and any source. Replace it with a rule limited to your management network or jump host addresses, and remove it from the Public profile entirely. An SSH server that answers on hotel Wi-Fi is a finding, not a feature.

Logging: the part everyone skips

Windows OpenSSH logs to the OpenSSH/Operational event channel, and by default almost nobody forwards it. If you run sshd, forward that channel to your log collector alongside Security events, and alert on repeated authentication failures and on successful logons from new source addresses. Also protect the log itself: an attacker with admin rights will try to clear it, so the copy that matters is the one already off the box.

While you are there, check the host keys. Each server generates its own host key pair in C:\ProgramData\ssh\. If those keys were copied from a gold image, every machine cloned from that image shares one identity, and host-key verification — the mechanism that tells a client it reached the right server — becomes meaningless. Regenerate host keys per machine during provisioning, and treat a changed host key as an event worth investigating, not a prompt worth clicking through.

SSH on Windows is a good tool. It just should not be an accidental one.
