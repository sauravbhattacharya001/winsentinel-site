Auditing Windows Installer Repair Abuse: When MSI Self-Healing Becomes Persistence

How attackers abuse Windows Installer repair actions and elevated custom actions for persistence, plus the controls and telemetry defenders should verify.

Windows Installer is built to make software resilient. If a user deletes a key file or registry value, an advertised shortcut or application launch can trigger msiexec.exe to repair the product automatically. That convenience creates a subtle persistence surface: an attacker who can alter an MSI source, transform, cached package, or repairable resource may turn a routine self-heal into code execution.

This is different from the well-known AlwaysInstallElevated misconfiguration. Repair abuse can exist even when that policy is disabled. The important questions are what causes repair, where Windows Installer obtains the repair material, and which security context executes custom actions.

How self-healing becomes an attack path

Windows Installer tracks products, components, key paths, and source locations. When a component's key path is missing, the installer can restore it from the registered package. Attackers look for weak links in that chain:

  • User-writable installation paths. A low-privilege user can replace a file that a privileged repair later consumes or loads.
  • Writable MSI source locations. Network shares, deployment caches, or local directories with weak ACLs let an attacker substitute installation content.
  • Unsafe custom actions. Deferred custom actions marked to run without impersonation can execute as SYSTEM during a privileged repair.
  • Untrusted transforms. Persistent transforms can modify installer behavior, including commands and files used during maintenance operations.
  • Repair triggers. Advertised shortcuts, COM activation, file associations, or an explicit msiexec /f command can activate the malicious path.
A signed MSI is not a permanent guarantee of safe repair. The effective trust boundary includes every source file, transform, cache directory, and custom action used after installation.

What defenders should inventory

Start with products installed for all users and correlate them with the Windows Installer registry under HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Installer. Do not delete entries from this database: inventory them, then validate the package and source locations.

Get-CimInstance Win32_Product |
  Select-Object IdentifyingNumber, Name, Version, LocalPackage

Get-ChildItem 'HKLM:\SOFTWARE\Classes\Installer\Products' |
  Select-Object PSChildName

Be cautious with Win32_Product in production: querying it can initiate consistency checks. Prefer your software inventory platform or registry-based collection at fleet scale. For each product, verify that LocalPackage resolves beneath the protected C:\Windows\Installer cache, inspect registered source paths, and test ACLs with Get-Acl. A standard user should not be able to modify machine-wide installer sources or deployed transforms.

Telemetry that exposes suspicious repairs

A normal repair is usually rare, attributable to a deployment, and limited to a known product. Investigate clusters of installer activity outside maintenance windows and repairs followed by unusual child processes.

  • Enable process creation auditing with command lines and monitor msiexec.exe launches containing /f, /fa, /fu, or unexpected TRANSFORMS= values.
  • Review the MsiInstaller Application log for repair and reconfiguration events, especially repeated repairs of the same product.
  • Alert when msiexec.exe spawns shells, script hosts, downloaders, or binaries from user-writable paths.
  • Watch for changes to .mst files, MSI source directories, and the installer cache. Modifications outside approved deployment workflows deserve immediate review.

Hardening the repair chain

  1. Protect sources with least privilege. Deployment shares should grant endpoints read access only; package publishing must require a separate administrative identity.
  2. Remove unsafe custom actions. Vendors should avoid elevated custom actions that consume user-controlled properties or paths.
  3. Require package integrity. Sign packages and transforms, validate hashes in deployment tooling, and investigate cache/source mismatches.
  4. Use application control. WDAC or AppLocker can prevent a repaired application from loading an unexpected executable, DLL, or script.
  5. Baseline and monitor. Record installed product codes, source paths, transform registrations, and directory ACLs so drift becomes visible.
