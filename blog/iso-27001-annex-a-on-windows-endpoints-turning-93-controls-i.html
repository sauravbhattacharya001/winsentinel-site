ISO 27001 Annex A on Windows Endpoints: Turning 93 Controls Into Audit Evidence

ISO 27001's Annex A controls sound abstract — here's how each one maps to a concrete, checkable setting on a Windows machine, and what WinSentinel's audits verify.

ISO 27001 certification conversations usually die in the same place: a spreadsheet of Annex A controls, a column marked "evidence," and a room full of people who cannot agree on what evidence actually looks like for a Windows endpoint. The standard is deliberately technology-neutral, which is a polite way of saying it never tells you which registry key, which policy, or which service proves a control is working. This post closes that gap for Windows machines — control by control, setting by setting.

The 2022 revision of Annex A has 93 controls across four themes: organizational, people, physical, and technological. Roughly a third of them land directly on endpoints. Those are the ones that sink audits, because they are the ones nobody can show on demand.

Start with the controls auditors actually sample

Auditors do not test all 93 controls with equal weight. They sample, and they sample where failure is cheap to prove. On Windows, that means these four first:

  • A.8.2 — Privileged access rights. Who holds local admin, and is it still justified? The evidence is the local Administrators group membership on each machine, the LAPS-managed password state, and whether any account holds SeDebugPrivilege or SeImpersonatePrivilege without a documented need. A machine with three stale admin accounts fails this control the moment the auditor asks for the list.
  • A.8.3 — Information access restriction. Can a standard user read the folders they should not? The evidence is NTFS permissions on shared and sensitive directories, plus whether SMBv1 or guest access is still enabled. Access restriction is not a policy document — it is the effective permissions on disk.
  • A.8.9 — Configuration management. Is the machine in its known-good state, and can you prove it? The evidence is a baseline: secure boot on, TPM 2.0 active, Windows Firewall rules as documented, Defender tamper protection enabled, and no drift from the approved configuration. "We configured it once" is not configuration management. A recorded baseline plus a current-state check is.
  • A.8.7 — Protection against malware. Is Defender real-time protection actually running, are exclusions documented, and is the engine current? An exclusion list nobody reviews is a hole an auditor will find in minutes — exclusions are the first thing a competent assessor asks to see.

The mapping discipline: one control, one checkable fact

The mistake most teams make is writing narrative evidence — paragraphs describing intent. Auditors discount intent and weigh facts. For every Annex A control that touches an endpoint, the evidence should be a single checkable statement:

"On this machine, at this time, this setting holds this value — and here is the check that produced it."

That is the entire discipline. A.8.5 (secure authentication) becomes: password policy enforces the documented length and complexity, reversible encryption is off, and cached credential counts are within policy. A.8.20 (network security) becomes: the firewall profile is active on all three profiles, inbound rules match the approved list, and no unexpected listening ports are open. A.8.10 (deletion of information) becomes: BitLocker is on, the recovery key is escrowed, and decommissioned drives are wiped per procedure. Each one is a machine fact, not a paragraph.

Where it gets interesting is scale. A single machine's evidence is one row. An ISO 27001 audit covers the fleet, and the standard's own logic — A.8.9 configuration management, A.8.15 logging, A.8.16 monitoring — is fleet logic: prove the control holds everywhere, and prove you would notice the day it stops holding somewhere. A practical sequence for your next audit cycle

  1. Pick the technological controls first. A.8.2, A.8.3, A.8.5, A.8.7, A.8.9, A.8.10, A.8.20 — these are the ones with machine facts behind them. Nail them before touching the organizational controls, which are mostly documents anyway.
  2. Audit one machine end to end. Run the full audit, and for every finding, write the control number next to it. You will discover that most findings map to two or three controls at once — a stale admin account is A.8.2 and A.8.5 and arguably A.5.15. That is fine; it means one fix closes several controls.
  3. Fix, then re-audit to prove the fix. The re-audit output is the evidence. Keep it timestamped. Auditors love a before-and-after pair far more than a clean first run, because it proves the control is operated, not just configured.
  4. Scale the baseline, not the effort. Once one machine's evidence set is clean, the question is whether the same statements hold on the other ninety-nine. That is a fleet question, and it is the one to answer before the auditor asks it — because they will.

ISO 27001 does not ask you to be perfect. It asks you to know your state, to be able to prove it, and to notice when it changes. On Windows endpoints, those are all checkable facts. Start with the machine in front of you.
