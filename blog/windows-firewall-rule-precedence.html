Windows Defender Firewall Rule Precedence: Why an Allow Rule Can Still Lose

Understand Windows Firewall rule precedence, profile scope, block-overrides-allow behavior, and how to audit effective policy before an outage or bypass.

A Windows administrator creates an inbound allow rule for a service, confirms that the port is correct, and still cannot connect. Another machine exposes the same service even though the local firewall console appears to deny it. These are not necessarily firewall bugs. They are usually failures to reason about effective policy: Windows Defender Firewall evaluates a merged set of local, Group Policy, MDM, service-hardening, and IPsec rules rather than a simple top-to-bottom list.

The rule list has no meaningful order

Unlike an edge firewall ACL, Windows rules do not win because they appear first or have a lower rule number. The filtering engine evaluates every applicable rule against direction, protocol, port, program, service, user, interface, address, and active profile. A rule that misses any condition is irrelevant to that packet.

The most important precedence rule is blunt: an explicit block overrides a conflicting explicit allow. Adding a broader allow rule does not neutralize an existing block. If one rule blocks TCP 445 for all programs and another allows TCP 445 for a backup agent, the block normally wins. The right repair is to remove or narrow the block after validating the risk, not to stack increasingly broad allows on top.

Windows Firewall is not “last rule wins.” Treat every block as a veto and every condition as part of the security boundary.

Defaults, explicit rules, and authenticated exceptions

A useful mental model is:

  • Explicit block rules defeat ordinary allow rules when both match.
  • Explicit allow rules permit traffic otherwise rejected by the profile's default inbound or outbound action.
  • Default profile behavior applies only when no explicit rule decides the flow. The usual secure posture is block inbound and allow outbound.
  • Allow-bypass rules are specialized authenticated exceptions. They can permit IPsec-authenticated traffic around certain block rules, but only when connection security requirements are correctly deployed.

That last category deserves caution. An allow-bypass rule is not a convenient stronger allow; it is part of an IPsec design. Deploying it without validating authentication scope can produce either an outage or a hole.

Profile scope causes the quietest failures

Domain, Private, and Public profiles may be active on different interfaces at the same time. A rule scoped only to Domain does nothing for a laptop whose network category changed to Public after DNS or domain-controller reachability failed. VPN and virtual adapters complicate this further.

Start troubleshooting with the active profile, then inspect all effective rules rather than only locally created ones:

Get-NetConnectionProfile
Get-NetFirewallProfile |
  Select-Object Name, Enabled, DefaultInboundAction, DefaultOutboundAction

Get-NetFirewallRule -PolicyStore ActiveStore |
  Where-Object Enabled -eq 'True' |
  Select-Object DisplayName, Direction, Action, Profile, PolicyStoreSourceType

ActiveStore shows the merged policy Windows is enforcing. PolicyStoreSourceType helps distinguish local rules from Group Policy and other sources. For one suspect rule, resolve its filters rather than trusting the display name:

$rule = Get-NetFirewallRule -PolicyStore ActiveStore `
  -DisplayName 'Allow Inventory API'
$rule | Get-NetFirewallPortFilter
$rule | Get-NetFirewallApplicationFilter
$rule | Get-NetFirewallAddressFilter
$rule | Get-NetFirewallServiceFilter

Local policy may be intentionally ignored

Enterprise policy can disable local rule merging. In that posture, a local administrator can create a rule and see it in the console, yet the rule will not affect the effective policy. This is desirable on tightly managed endpoints because malware with administrative rights cannot open its own inbound path. It is also why emergency firewall changes must be made through the authoritative policy channel instead of improvised locally.

Audit the profile settings and policy source before declaring a firewall malfunction. Also check whether the executable path, Windows service name, remote address scope, interface type, and edge-traversal condition match the real flow. Port-only reasoning misses most modern rule constraints.

A safe troubleshooting workflow

  1. Identify the exact five-tuple, direction, process, service, interface, and active profile.
  2. Query ActiveStore and locate every matching allow and block rule.
  3. Inspect each rule's port, application, service, address, profile, and authentication filters.
  4. Confirm whether local rule merging is allowed and which policy store owns the result.
  5. Use firewall logging or Windows Filtering Platform audit events to prove the decision; do not disable the firewall as a test.
  6. Narrow or remove the conflicting rule, retest, and document the intended exception.
